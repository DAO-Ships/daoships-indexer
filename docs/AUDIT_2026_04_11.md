### ~~C3.~~ H10. Non-Atomic Read-Modify-Write on DAO Totals (downgraded to MEDIUM)
- **Files:** `src/handlers/daoship.ts` lines 56-74, 468-480, 817-823
- **Category:** Stability (CWE-362)
- **Original claim:** Supabase HTTP API eventual consistency causes stale reads between concurrent events.
- **Validated finding:** The eventual consistency claim is wrong -- PostgreSQL is strongly consistent and the processing loop is strictly sequential (no `Promise.all` anywhere in `src/`). The real risk is a narrow crash window: if the process dies after `updateDao` but before `markLogProcessed` (processor.ts:177), the delta is double-applied on restart. The window is microseconds. Existing mitigation: reorg recovery (schema.sql:536-540) recalculates totals from `SUM(ds_members)`, but only fires on reorg detection, not plain crash+restart.
- **Fix:** Create atomic SQL function `ds_adjust_dao_totals(p_dao_id, p_delta, p_token_type, p_tx_hash, p_log_index)` that checks dedup table + applies delta in one transaction, eliminating the crash window entirely.

### ~~C4.~~ M16. Member Balances Not Cleaned on Reorg (downgraded to MEDIUM)
- **File:** `supabase/migrations/schema.sql` lines 524-529
- **Category:** Stability
- **Original claim:** Member balances are permanently corrupted after any reorg.
- **Validated finding:** The claim is technically correct for fork-exclusive Transfer events, but practically mitigated by `CONFIRMATION_BLOCKS` (default 5 for mainnet). Only reorgs deeper than the confirmation window affect indexed data, and those are extremely rare. The comment "self-heals as the correct events replay" is misleading for fork-exclusive events but the follow-up "for deep reorgs, a full re-index is required" is the correct operational guidance. All fix options (delta tracking table, on-chain balanceOf queries, member reset+rebuild) add significant complexity for a 0.1% edge case.
- **Fix:** Update the comment at schema.sql:524-529 to be more precise: replace "self-heals" language with explicit acknowledgment that fork-exclusive Transfers leave stale deltas and a full re-index is required for deep reorgs.

## HIGH -- all resolved

### ~~H1. `create_ds_schema` / `drop_ds_schema` Accept Arbitrary Schema Names~~ -- FIXED (downgraded to LOW)
> Added schema name whitelist (`testnet`, `mainnet`, `dev`, `public`) to both `create_ds_schema` and `drop_ds_schema`. Defense-in-depth; not a real attack surface since function execution is already revoked from public roles.

### ~~H2. `INavigatorAbi` Re-instantiated on Every NavigatorSet Event~~ -- FIXED
> Hoisted to module scope: `const iNavIface = new Interface(INavigatorAbi);` in daoship.ts:27.

### ~~H3. `handleNavigatorSet` Scans Potentially Massive Block Range~~ -- FIXED (downgraded to MEDIUM)
> Reversed search direction (backwards from NavigatorSet block) and added module-level LRU cache for NavigatorDeployed metadata (immutable constructor data, max 500 entries). Cache is cleared on reorg recovery alongside the navigator DAO cache.

### ~~H4. `handleMintOrBurn` Missing Parallel Array Length Validation~~ -- FIXED (downgraded to LOW)
> Added defensive length check matching the pattern in `handleRagequit`. Logs error and returns early on mismatch.

### ~~H5. No DB Request Batching~~ -- FIXED (downgraded to MEDIUM)
> Parallelized independent `getMember` reads in `handleTransfer` via `Promise.all` when both sender and receiver exist and are different members. Self-transfers remain sequential to avoid stale reads.

### ~~H6. `ds_increment_proposal_votes` Runs 4 Subqueries Per Vote~~ -- FIXED (downgraded to LOW)
> Added composite index `idx_ds_votes_proposal_approved ON ds_votes(proposal_id, approved)` to speed up the idempotent vote tally derivation.

### ~~H7. RLS Policies Expose `ds_indexer_state` to Public~~ -- FIXED (downgraded to LOW)
> Added SQL comment documenting that the public read policy is intentional for frontend sync status display. The indexer is a read-only observer; exposing sync state has no on-chain security impact.

### ~~H8. Alpha-Quality Blockchain SDK~~ -- N/A
> `quais` alpha is the best available SDK for Quai Network. Accepted risk.

### ~~H9. Health Check Binds to All Interfaces~~ -- FIXED (downgraded to MEDIUM)
> Added `HEALTH_CHECK_HOST` config option (defaults to `0.0.0.0` for Docker compatibility). Bare-metal deployments can set to `127.0.0.1` to restrict access.

### ~~H10~~ -- see C3 above -- FIXED
> Replaced read-modify-write pattern with atomic SQL function `ds_adjust_dao_totals` in schema.sql, database.ts, and daoship.ts. All three call sites (handleMintOrBurn, handleRagequit, handleConvertSharesToLoot) now use server-side atomic delta adjustment. 227 unit tests pass.

## Strengths Identified

The codebase demonstrates mature engineering practices:

- **Idempotency:** `ds_processed_logs` dedup table prevents double-processing on retry
- **Reorg handling:** Block hash checks, walkback windows, registry rebuilding
- **Security hardening:** RLS on all tables, prototype pollution prevention, JSONB sanitization, URL scheme validation, XSS prevention
- **Trust model:** Clear UNTRUSTED -> VERIFIED hierarchy for Poster content
- **Operational safety:** Config deep-freeze, non-enumerable service key, log redaction, graceful shutdown with interruptible sleep
- **Schema design:** Proper `NUMERIC(78,0)` for uint256, generated columns, appropriate indexes
- **Circuit breaker & rate limiting:** On RPC calls with exponential backoff
- **Docker security:** Multi-stage build, non-root user, dev deps excluded from production image
- **X-Forwarded-For trust:** Configurable, defaults to not trusting
